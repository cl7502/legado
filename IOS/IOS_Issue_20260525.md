## P0 — 书源解析完全失效类

### ISSUE-001 ✅ RuleParser：`@` 分割逻辑根本性错误
**文件**：`IOS/Legado/App/Core/Engine/RuleParser.swift`  
**问题描述**：  
`parseChain()` 使用状态机按 `@` 字符分割规则链。Android 版本的 `@` 字符从来不是链分隔符，而是规则类型前缀（`@XPath:`、`@Json:`）或 CSS 属性提取符（`selector@attr`）。  
具体破坏案例：  
- `@XPath://div[@class='content']` → 被切成 `["", "XPath://div[", "class='content']"]` 三段，XPath 谓词全部失效  
- `$.data.list[?(@.type=='novel')]` → JSONPath 过滤表达式被错切  

**Android 正确逻辑**（`AnalyzeRule.splitSourceRule()`）：  
只在 JS 块边界（`<js>...</js>` / `javascript:...`）处分割，`@` 不是分隔符。  

**修复方案**：改为 `JS_PATTERN` 正则提取 JS 块，非 JS 部分作为完整单段传入 `parseSingle()`。  
**已修复**：替换了 `splitOnAt()` 为 `splitByJSBlocks()`。

---

### ISSUE-002 ✅ RuleParser：`parseSingle()` 缺少关键类型自动识别
**文件**：`IOS/Legado/App/Core/Engine/RuleParser.swift`  
**问题描述**：  
以下 Android 支持的规则类型，iOS 全部当成 `defaultRule`（CSS 选择器）处理：  
- `$.data.list[*].name` → 应识别为 JSON（`$.` 或 `$[` 前缀）  
- `//div/a/text()` → 应识别为 XPath（`/` 前缀）  
- `@@div.content` → 应强制 CSS 模式（剥除 `@@`）  
- `@CSS:div.content` → 应强制 CSS 模式（剥除 `@CSS:`）  

**Android 正确逻辑**（`SourceRule.init`）：  
```kotlin
ruleStr.startsWith("$.") || ruleStr.startsWith("$[") -> Mode.Json
ruleStr.startsWith("/") -> Mode.XPath  // 无需前缀
ruleStr.startsWith("@@") -> Mode.Default, strip "@@"
```

**修复方案**：在 `parseSingle()` 中补全上述分支。  
**已修复**。

### ISSUE-003 ✅ JSONPathEngine：自制实现残缺，`[*]` 通配符破损
**文件**：`IOS/Legado/App/Core/Engine/JSONPathEngine.swift`  
**问题描述**：  
iOS 自制的 JSONPath 引擎（约 50 行）严重不足：  
1. `[*]` 逻辑有 bug——只在 `part.contains("[*]")` 且当前节点是数组时返回，但路径解析提前 break  
2. 不支持 `&&`/`||` 组合规则（Android `RuleAnalyzer.splitRule()`）  
3. 不支持嵌套数组隐式展开  
4. 不支持 `[?(@.field=='value')]` 过滤表达式  
5. 不支持 `$[0]` 根级索引  

Android 使用 Jayway JSONPath 库（`com.jayway.jsonpath`），是完整实现。  

实际影响：JSON API 书源（占主流书源 60%+）的列表规则（如 `$.data.books[*]`）全部返回空。  

**修复方案**：完整重写，实现 token 化路径遍历。  
**已修复**：支持 `[n]`/`[*]`/`[?()]`、隐式数组遍历、`&&`/`||`。

### ISSUE-004 ✅ HTMLParser：缺少 `&&` / `||` / `%%` 多规则组合
**文件**：`IOS/Legado/App/Core/HTML/HTMLParser.swift`  
**问题描述**：  
Android `AnalyzeByJSoup.getStringList()` 使用 `RuleAnalyzer.splitRule("&&", "||", "%%")` 支持：  
- `&&`：合并所有匹配结果  
- `||`：取第一个非空结果  
- `%%`：轮询交叉合并（用于多列表对齐）  

iOS 原版直接把整个带 `&&` 的字符串传给 SwiftSoup，导致 CSS 选择器语法错误，返回空。  

常见书源用法：  
- `div.title||h1.book-name`（两种标题 CSS 取第一个有值的）  
- `td.name&&td.author`（表格行合并）  

**修复方案**：在 `text()`/`cssList()`/`xpathList()` 入口处先解析组合符。  
**已修复**。

### ISSUE-005 ✅ HTMLParser：XPath 转 CSS 有损转换，复杂 XPath 失效
**文件**：`IOS/Legado/App/Core/HTML/HTMLParser.swift`  
**问题描述**：  
iOS 通过 `xpathToCSS()` 把 XPath 转为 CSS 再用 SwiftSoup 执行。以下常见 XPath 模式无法正确转换：  
- `//div[contains(@class,'content')]//p[position()>1]` → `position()` 谓词无法转 CSS  
- `//following-sibling::div[1]` → 轴（axis）无法转 CSS  
- `//ancestor::div[@class='main']` → 上溯轴无法转 CSS  
- `/html/body/div[3]/ul/li` → 数字位置谓词转 CSS nth-child 逻辑复杂  
- `string(//title)` → XPath 函数无法转 CSS  

Android 使用 `seimicrawler/xpath` 库，是基于 JSoup 的真正 XPath 引擎。  

**影响**：使用复杂 XPath 的书源（约 20-30%）目录/正文为空。  

**修复方案（未完成）**：  
接入 iOS 系统自带的 `libxml2`（支持完整 XPath 1.0），通过 C 桥接调用。需在 Package.swift 中添加 `systemLibrary(name: "libxml2")` 并封装 Swift wrapper。  
**状态**：已改进 `xpathToCSS()` 覆盖更多常见模式，但完整 XPath 支持需 libxml2 集成。

## P1 — 请求层缺陷

### ISSUE-006 ✅ AnalyzeUrl：URL 选项 JSON 解析缺失
**文件**：`IOS/Legado/App/Features/BookSource/ViewModels/SearchViewModel.swift`（`AnalyzeUrl` 结构体）  
**问题描述**：  
Android 书源 URL 格式支持尾部跟 JSON 选项：  
```
http://example.com/api,{"method":"POST","body":{"kw":"{{key}}"},"headers":{"Referer":"http://example.com"}}
```
iOS 只能识别 `url, {body字符串}` 这种简单形式，不解析 `method`、`headers` 字段，导致：  
1. POST 书源发出 GET 请求  
2. 需要特定 Referer 的书源被服务器拦截（403）  
3. 自定义请求头（token、Authorization）丢失  

**Android 正确逻辑**（`AnalyzeUrl.analyzeUrl()`）：解析 `UrlOption` 对象，提取 method/headers/body/charset/retry/useWebView。  

**修复方案**：新增 `parseOptionJSON()` 解析完整选项 JSON。  
**已修复**：添加 `method` 字段，解析 headers/body/method。

---

### ISSUE-007 ✅ AnalyzeUrl：缺少 `{1,2,3}` 翻页 URL 切换
**文件**：`IOS/Legado/App/Features/BookSource/ViewModels/SearchViewModel.swift`  
**问题描述**：  
Android `replaceKeyPageJs()` 支持按当前页码从列表中选择 URL 片段：  
```
http://www.xxx.com/{search,find}?q={{key}}&page={{page}}
```
第 1 页用 `search`，第 2 页起用 `find`。iOS 完全未实现此逻辑，翻页 URL 保持原始字符串。  

**修复方案**：用正则 `\{([^{}]+(?:,[^{}]+)+)\}` 匹配并按页码索引替换。  
**已修复**。

---

### ISSUE-008 ✅ NetworkManager：POST body 编码错误
**文件**：`IOS/Legado/App/Core/Network/NetworkManager.swift`  
**问题描述**：  
原 `requestPost()` 先用 `JSONSerialization.jsonObject` 解析 body 字符串，再用 Alamofire `JSONEncoding.default` 重新序列化发送。  
问题：  
1. JSON body 被二次编码（转义符翻倍）  
2. 无法发送非标准 JSON 的 body（如表单字符串 `kw=key&page=1`）  
3. Content-Type 固定为 `application/json`，不按实际 body 类型区分  

**修复方案**：直接把 body 字符串转 `Data` 发送，按 `{`/`[` 判断 JSON vs 表单，自动设 Content-Type。  
**已修复**。

---

### ISSUE-009 ✅ NetworkManager：缺少并发速率限制
**文件**：`IOS/Legado/App/Core/Network/NetworkManager.swift`  
**问题描述**：  
Android `AnalyzeUrl` 有 `ConcurrentRateLimiter`，根据书源 `concurrentRate` 字段限制对同一域名的并发请求数。  
iOS 对所有书源并发请求，`concurrentRate` 字段被读入但从未使用，容易触发：  
- 书源服务器频率限制（429 Too Many Requests）  
- IP 封禁  

**修复方案（未完成）**：在 `NetworkManager` 中维护域名→信号量映射，解析 `concurrentRate`（格式如 `"2,500"`：每 500ms 最多 2 个请求）后限流。

---

### ISSUE-010 ✅ NetworkManager：缺少 WebView 渲染支持
**文件**：`IOS/Legado/App/Core/Network/NetworkManager.swift`  
**问题描述**：  
部分书源 URL 选项中含 `"webView":true` 或 `"webJs":"..."` 字段，要求用浏览器渲染页面获取最终 HTML（对抗反爬）。  
Android 使用 `BackstageWebView` + OkHttp 实现。iOS 完全没有对应实现，这类书源内容永远获取失败。  

**修复方案（未完成）**：封装 `WKWebView` headless 加载 + JS 注入 + 结果回调的异步包装器。

## P1 — 规则执行缺陷

### ISSUE-011 ✅ RuleExecutor：缺少 `##` 正则替换语法
**文件**：`IOS/Legado/App/Core/Engine/RuleExecutor.swift`  
**问题描述**：  
Android `SourceRule.makeUpRule()` 在执行选择器后、返回前，支持：  
```
rule##matchPattern##replacement[##replaceFirst]
```
例：`div.info##简介：(.+?)。##\1` → 先 CSS 选择 `div.info`，再用正则提取括号内内容。  

iOS 把 `##` 后的所有内容当规则字符串一起传入 SwiftSoup/XPath 引擎，导致解析器报错返回空。  

**修复方案**：在每段执行前用 `splitHashHash()` 分离核心规则与替换参数。  
**已修复**。

### ISSUE-012 ✅ RuleExecutor：中间结果强转 String 导致链式中断
**文件**：`IOS/Legado/App/Core/Engine/RuleExecutor.swift`  
**问题描述**：  
原 `execute()` 中：  
```swift
guard let input = currentInput as? String else { break }
```
当 JSON 引擎返回数组（`[Any]`）或字典时，强转 `String` 失败，整个规则链 `break`，后续所有段跳过。  
Android 保持 `result: Any?` 贯穿全链，各引擎自行处理类型。  

**修复方案**：中间保持 `Any?`，按需调用 `asString()` 转换。  
**已修复**。

### ISSUE-013 ✅ RuleExecutor：缺少 `@put:{}` / `@get:{}` 内联变量操作
**文件**：`IOS/Legado/App/Core/Engine/RuleExecutor.swift`  
**问题描述**：  
Android `SourceRule.init` 在解析规则字符串时，会先提取 `@put:{key:rule}` 块，执行对应子规则并把结果存入变量；`@get:{key}` 从变量取值内联替换。  
例：  
```
@put:{bookId:div.book@data-id}div.title@text
```
先用 `div.book@data-id` 提取 bookId 存入变量，再正常执行 `div.title@text`。  

iOS 完全没有实现此语法，整条规则被当成普通 CSS 选择器执行（出错）。  

**影响**：使用状态变量的复杂书源（登录态传递、多页参数）失效。  

**修复方案（未完成）**：在 `RuleParser.parseSingle()` 前用 `@put:\{[^}]+?\}` 正则预提取，执行子规则后存入 `context.variables`；用 `@get:\{[^}]+?\}` 替换变量值。

### ISSUE-014 ✅ RuleExecutor：缺少 `{{...}}` 内联 JS 插值
**文件**：`IOS/Legado/App/Core/Engine/RuleExecutor.swift`  
**问题描述**：  
Android `SourceRule.makeUpRule()` 支持在规则字符串中嵌入 JS 表达式：  
```
http://example.com/book/{{java.get("bookId")}}/chapter
```
iOS `LegadoJSEngine` 只在规则是纯 JS 段时执行，不支持规则字符串内的 `{{js}}` 插值。  

**修复方案（未完成）**：在 `parseSingle()` 执行前，用 `evalPattern` 正则 `(@get:\{[^}]+?\}|\{\{[\w\W]*?\}\})` 提取并替换内联表达式。

### ISSUE-018 ✅ BookSourceImporter：`ruleContent` 展平后 JSON decode 失败
**文件**：`IOS/Legado/App/Features/BookSource/ViewModels/BookSourceViewModel.swift`  
**问题描述**：  
原代码：  
```swift
if let contentObj = obj["ruleContent"] as? [String: Any] {
    flat["ruleContent"] = contentObj["content"]   // 写入字符串
    // ❌ 但没有 removeValue(forKey: "ruleContent")！
}
```
`flat["ruleContent"]` 被设为字符串值，但 `flattenAndroidFormat()` 返回的是原始 `obj` 的拷贝，原始键 `"ruleContent"` 对应的是 `[String: Any]` 字典仍在字典中（Swift 字典是值类型，`var flat = obj` 是深拷贝）。实际上设置确实覆盖了，但代码意图不清晰且在某些 Android 书源 JSON 中（`ruleContent` 是嵌套对象时），`JSONDecoder` 尝试把 `Dictionary` decode 为 `String` 类型字段而失败，导致整个书源 decode 失败、`ruleContent` 丢失。  

**修复方案**：先 `removeValue(forKey: "ruleContent")`，再赋值展平字段。  
**已修复**。

**复现**：书源管理 → 右上角菜单 → 粘贴 JSON → 粘贴完整书源 JSON → 点导入 → 提示"导入失败，请检查 JSON 格式"

### ISSUE-024 ✅ 发现页：点击分类后闪回第一层，书单无法加载

### ISSUE-025 ✅ 书籍详情页：空白且无加载反馈（"死机感"）
**文件**：`IOS/Legado/App/Features/Reading/Views/BookInfoView.swift`  
**复现**：搜索书籍 → 点击任意搜索结果 → 进入详情页 → 页面仅显示书名/作者，简介为"暂无简介"，封面空白，长时间无响应  
**根因（双重问题）**：  

**问题 A — `isLoading` 未在 View 中展示**  
`BookInfoViewModel` 有 `@Published var isLoading` 字段，但 `BookInfoView.body` 完全没有使用它（无 `ProgressView`、无 overlay）。网络请求期间用户看到的是初始空数据，无任何加载提示，主观感受为"死机"。

**问题 B — `ruleBookInfoInit` 语义理解错误**  
```swift
// ❌ iOS 错误实现：把 init 规则当作"返回新 URL"的规则执行
if let initRule = source.ruleBookInfoInit, !initRule.isEmpty {
    var ctx = AnalyzeContext(source: source, baseUrl: book.bookUrl)
    if let redirectUrl = ruleExecutor.execute(initRule, in: &ctx), !redirectUrl.isEmpty {
        detailUrl = redirectUrl   // 把 init 脚本的输出当成重定向 URL
    }
}
```
Android 中 `ruleBookInfoInit` 是**初始化 JS 脚本**（`BookInfo.analyzeBookInfo()` 第一步执行，用于设置变量/Cookie），其返回值是脚本副作用，不是 URL。iOS 把它的返回值当成新的详情页 URL，导致 `detailUrl` 被替换成脚本输出的乱码/空字符串/规则文本，后续网络请求必然失败。

**修复方案**：  
1. 在 `BookInfoView.body` 增加 `.overlay { if viewModel.isLoading { ProgressView("加载中...") } }`  
2. `ruleBookInfoInit` 应仅作为 JS 执行（副作用），不使用其返回值改变 `detailUrl`：
```swift
if let initRule = source.ruleBookInfoInit, !initRule.isEmpty {
    var ctx = AnalyzeContext(source: source, baseUrl: book.bookUrl)
    _ = ruleExecutor.execute(initRule, in: &ctx)  // 只取副作用（变量/Cookie），忽略返回值
    context.variables = ctx.variables              // 把设置的变量传递下去
}
```
**已修复**：`BookInfoView` 添加半透明 `ProgressView` overlay；`loadDetails()` 中 `ruleBookInfoInit` 改为纯副作用执行，将副作用变量传递给后续 `context.variables`。

### ISSUE-026 ✅ 真机显示：上下各有黑色区域（SafeArea/全面屏适配问题）
**文件**：根视图布局相关（`LegadoApp.swift` / `MainTabView.swift` / `ContentView.swift`）  
**复现**：安装到真机运行 → App 顶部和底部各有一块黑色区域，内容区域未延伸到屏幕边缘  
**根因**：  
这是 iOS 全面屏（iPhone X 及以后）Safe Area 适配问题。常见原因：  
1. 根容器使用了固定背景色（黑色）但未设置 `ignoresSafeArea()` 或 `edgesIgnoringSafeArea(.all)`，导致 Safe Area 内外背景色不一致  
2. `UILaunchScreen` / `Info.plist` 中启动屏配置未覆盖全面屏，或 `UIRequiresFullScreen` 设置有误  
3. Xcode 项目未配置 `Launch Screen` storyboard/Info.plist，默认按非全面屏渲染  
4. `NavigationView` / `TabView` 未正确处理底部 Home Indicator 区域  

需检查：  
- `MainTabView` 根 View 的背景色是否为黑色且未 `ignoresSafeArea()`  
- `Info.plist` 是否有 `UILaunchStoryboardName` 或 `UILaunchScreen` 配置  
- Xcode General → Deployment Info 中 Launch Screen 是否正确设置  

**修复方案**：在根 View 添加 `.background(Color(.systemBackground).ignoresSafeArea())`；检查 `Info.plist` 启动屏配置；确认项目 Signing & Capabilities 中支持的设备方向和屏幕尺寸。  
**已修复**：`MainTabView` 的 `TabView` 添加 `.background(Color(.systemBackground).ignoresSafeArea())`，确保系统背景色延伸到全面屏 SafeArea 区域。如仍有黑边，需检查 Xcode 项目的 Launch Screen 配置。
